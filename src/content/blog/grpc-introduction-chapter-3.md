## 1  Empty Messages in gRPC

Sometimes an RPC doesn’t need any input or output data. Instead of inventing an `Empty {}` message yourself, you can import Google’s built‑in `google.protobuf.Empty` – a universal “no‑fields” message already generated by the tooling.

```proto
syntax = "proto3";
import "google/protobuf/empty.proto";
package example;

service HealthCheck {
  // Ping returns immediately if the server is alive.
  rpc Ping (google.protobuf.Empty) returns (google.protobuf.Empty);
}
```

### How it works
- By importing `google/protobuf/empty.proto` we gain access to a ready‑made **empty request/response** type.
- The `Ping` method therefore signals: “No payload needed, success or failure is enough information.”
- The generated TypeScript bindings will include an `Empty` class you can directly instantiate.

### Server implementation (TypeScript)

```ts
import * as grpc from '@grpc/grpc-js';
import { Empty } from 'google-protobuf/google/protobuf/empty_pb';
import { HealthCheckService, IHealthCheckServer } from './generated/example_grpc_pb';

// 1️⃣ Implement the service interface produced by protoc‑gen‑ts.
const healthImpl: IHealthCheckServer = {
  // The input argument carries nothing useful, so we ignore call.request.
  ping(call, callback) {
    console.log('[Server] Ping received');

    // 2️⃣ Return an Empty instance → success.
    callback(null, new Empty());
  },
};

// 3️⃣ Bind implementation to a gRPC server.
const server = new grpc.Server();
server.addService(HealthCheckService, healthImpl);
server.bindAsync('0.0.0.0:50051', grpc.ServerCredentials.createInsecure(), () => {
  server.start();
  console.log('[Server] running on :50051');
});
```

> **Why `callback(null, new Empty())`?** The first parameter is the error (here `null` = success). The second is the response message – an Empty instance conveys “OK”.

### Client call (TypeScript)

```ts
import * as grpc from '@grpc/grpc-js';
import { Empty } from 'google-protobuf/google/protobuf/empty_pb';
import { HealthCheckClient } from './generated/example_grpc_pb';

const client = new HealthCheckClient('localhost:50051', grpc.credentials.createInsecure());

// 1️⃣ Create an Empty request (or just `{}` – both work).
client.ping(new Empty(), (err) => {
  if (err) return console.error('Ping failed:', err);

  // 2️⃣ No payload to parse ✓
  console.log('✅ Server is alive');
});
```

The empty‑type pattern is perfect for **health checks**, **ready probes**, **cache‑clear commands**, or any “fire‑and‑forget” RPC.

## 2  Deadlines and Timeouts

Without a deadline, a misbehaving server (or flaky network) could leave your client hanging forever. A **deadline** is an absolute **timestamp** at which the RPC should be aborted if it hasn’t finished. gRPC will surface a `DEADLINE_EXCEEDED` error to the client and **automatically cancel work on the server**.

```ts
import * as grpc from '@grpc/grpc-js';
import { WorkRequest, WorkResponse, WorkServiceClient } from './generated/work_grpc_pb';

const client = new WorkServiceClient('localhost:50051', grpc.credentials.createInsecure());

// Build request payload
const request = new WorkRequest();
request.setPayload('do something');

// 👉 Deadline 5 seconds from now
const deadline = Date.now() + 5_000;

client.doWork(request, { deadline }, (err, res?: WorkResponse) => {
  if (err) {
    // 1️⃣ Check for a timeout specifically
    if (err.code === grpc.status.DEADLINE_EXCEEDED) {
      return console.error('⏰ Timed out – server took too long');
    }
    return console.error('RPC failed:', err);
  }

  // 2️⃣ Normal happy‑path
  console.log('Result:', res!.getResult());
});
```

### What’s happening?
- The client *sends* the deadline timestamp in the HTTP/2 headers.
- The gRPC library *starts a watchdog timer*; if no response arrives in time, it returns the timeout error.
- The server runtime sees the deadline and **automatically closes the call** once the time passes.

#### Checking cancellation on the server
Long‑running handlers should peek at `call.cancelled` so they can abandon heavy computation once the client is no longer waiting:

```ts
while (doingWork) {
  if (call.cancelled) {
    console.log('Client gave up – aborting work');
    break;
  }
  // ... continue expensive processing
}
```

A good rule of thumb: **always set a deadline** that matches how patient your user (or upstream service) should be.

## 3  Load Balancing & Retry (client‑side)

Your production service likely spins up *multiple* pods/VMs for the same gRPC server. A single DNS name (or service discovery entry) often returns **multiple IPs**. Let’s teach the Node client to **round‑robin** across them *and* automatically retry transient failures.

### 3.1  Round‑robin load balancing

```ts
import * as grpc from '@grpc/grpc-js';
import { ExampleClient } from './generated/example_grpc_pb';

// gRPC “service config” JSON enabling round_robin
const serviceConfig = {
  loadBalancingConfig: [{ round_robin: {} }],
};

const client = new ExampleClient(
  // dns:/// hint tells gRPC to resolve the host via DNS and use every A‑record
  'dns:///myservice.default.svc.cluster.local:50051',
  grpc.credentials.createInsecure(),
  {
    'grpc.service_config': JSON.stringify(serviceConfig),
  },
);
```

**How does this work?**
1. `dns:///…` instructs the resolver to *fetch every A‑record* from DNS.
2. The channel installs the **round‑robin picker** – each new RPC picks the next sub‑connection, spreading load roughly evenly.
3. No Envoy / external balancer needed for simple setups.

### 3.2  Automatic retries for idempotent RPCs

For operations safe to repeat (e.g. **GET‑like** reads), you can ask gRPC to retry on `UNAVAILABLE` – the canonical “server temporarily unreachable” code.

```ts
const retryingConfig = {
  methodConfig: [
    {
      // Apply policy to every RPC in this service
      name: [{ service: 'example.Example' }],
      retryPolicy: {
        maxAttempts: 3,              // total tries = 3
        initialBackoff: '0.1s',      // wait 100 ms before first retry
        maxBackoff: '1s',            // cap delay at 1 s
        backoffMultiplier: 2,        // exponential (0.1 → 0.2 → 0.4 …)
        retryableStatusCodes: ['UNAVAILABLE'],
      },
    },
  ],
  loadBalancingConfig: [{ round_robin: {} }],
};

const client = new ExampleClient(
  'dns:///myservice.default.svc.cluster.local:50051',
  grpc.credentials.createInsecure(),
  { 'grpc.service_config': JSON.stringify(retryingConfig) },
);
```

**Flow**
1. Client sends request ➜ server crashes mid‑flight → returns `UNAVAILABLE`.
2. gRPC waits 100 ms then re‑issues the call to the *next* backend.
3. If that fails too, wait 200 ms, try again. Third failure surfaces back to the app.

Retries + LB together provide **graceful fail‑over** with zero application code.

> ⚠️ Use retries only for **idempotent** calls. Don’t retry a money transfer or “create‑record” blindly – you could cause duplicates.
